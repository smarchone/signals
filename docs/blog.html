Notes on working with agents · signals

Steer decisions,
not prompts.

If you're stuck steering coding agents one prompt at a time, what should you steer them with instead? And what does a tool built on the answer look like?

Steering an agent looks like a prompting problem. So we write longer prompts, then specs, then a context file that grows every week. It works for a day. Then a new session starts and you say it all again: SQLite, ISO dates, no lodash. The agent builds, and forgets whichever one you left out.

Steer with prompts and you steer procedures forever.
Steer decisions, and agents steer the procedures.

Both panels make the same six calls. Steering prompts, each call lives in a prompt, and the prompt dies with its session. So every prompt carries all the old calls again, and any you skip, the build quietly undoes. Steering decisions, each call lands once and every build follows it. You're asked three times, all for calls that are actually yours.

Same calls, same agent. The only difference is where a decision lives. So that's the design question: where should it live, what goes there, and how does it steer?

Decisions need a home

Today they have none that lasts. Prompts and sessions forget. Specs hold decisions, but frozen on day one, so they're stale by build two. Context files and memory keep everything, kept by hand or by habit, until it's noise. The rest stays in your head as tribal knowledge.

What a decision holds

A prompt says what to do now. A decision says what's true, why, and what was ruled out.

A prompt, build six
use sqlite. dates in ISO.
don't add lodash again.
and no, still not postgres.
A decision, once
arch/data#sqlite
what:    SQLite for storage
why:     single user, zero ops
why not: Postgres
revisit: a second user exists

The why not is what stops the agent re-arguing Postgres on every build, and revisit says when it's fair to. Written this way, a decision keeps steering long after the task that made it. That's why it should be the source of truth, with context, docs and code derived from it.

Code shouldn't be a derivative of specs.
It's a derivative of decisions.

But write down every decision and you've rebuilt the noise. So the next question is which ones.

One test, one owner

Signals keeps decisions in .decisions/ and asks one question of each candidate, no matter who made it: would rebuilding from the store alone get this wrong, or would changing it later need an executive to decide again? If yes, it goes to the role that owns it:

  • CEOWhy and for whom. Audience, non-goals, budget, big bets.
  • PMWhat is built. Feature scope, user-facing rules and behaviour.
  • ArchitectHow it is built. Stack, data, boundaries, security posture.
  • DetailEverything else. A library inside the agreed stack, naming, file layout. Never stored; the agent just proceeds.

Most decisions are details. That's what keeps the store small enough to read, for you and for the agent. The rest land in the smallest partition that covers them, like pm/onboarding or arch/auth, so a task loads only what it touches. And the store never holds a conflict: a new decision either fits, or comes to you.

You're the board

That leaves you the board's job. Boards don't read every pull request, and engineers don't re-argue strategy before each commit, because both work from the same calls. The store is that shared page. The agent asks it before choosing, and proposes a decision when it's about to make a call an executive would own. You approve every executive decision and settle every conflict. Plans are reviewed in one batch with /signals update; a call made mid-build waits for your answer before the agent builds on it. You never get asked about variable names.

Put together: decisions get a home, a test keeps the home small, each one has an owner, builds obey them, and your attention goes only where a call is yours to make.

Decide once.
Every build follows.
